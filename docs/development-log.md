### 보안 관련 경고 ⚠️

- **원격 MCP 엔드포인트는 인터넷에 노출된 쓰기 가능 경로**다. HTTPS·토큰 만료·Rate Limit·Origin 검증 없이 열면 안 된다 (architecture.md 4.2.1).
- **공개 URL로 실배포**하므로 데모 계정은 조회 전용으로 분리하고, 쓰기 권한 계정은 공개하지 않는다. MySQL/Redis 포트는 외부에 열지 않는다(Compose 내부 네트워크만). SSH는 키 인증 + IP 제한.

- **MCP에 쓰기 권한 토큰을 주는 것 자체가 위험**하다. 게임 데이터(닉네임, 우편 본문)에 섞인 문구로 AI가 오동작할 수 있어 확인/승인 절차와 토큰 최소 권한이 필수다.
- 시뮬레이터용 `/internal/game/*` 라우터는 운영 환경에서 비활성화되어야 한다. 활성화된 채 배포되면 인증 없이 재화를 만들 수 있는 경로가 된다.
- 시드 운영자 비밀번호는 `.env`로만 주입한다. 공개 데모를 띄울 경우 별도 데모 계정(조회 전용)을 둔다.

### 발생 이슈

1. **argon2 timeCost 하한** — argon2 0.41.1은 `timeCost >= 2`를 강제. 테스트용 설정(1)에서 `Invalid timeCost` 발생 → 테스트 설정을 2로, 환경변수 검증 하한도 2로 수정.
2. **Docker 이미지** — argon2 사전 빌드가 glibc용만 있어 Alpine(musl)에서 동작 불가 → `api.Dockerfile` 베이스를 `node:22-slim`으로 변경.

## 2026-11-10 — 랭킹 기록 순서 번호: DB 카운터 → 시간 기반 (핫 로우 제거) ✅ 완료

### 문제

| 문제 | 내용 |
|---|---|
| 핫 로우 | 순서 번호를 시즌 행 `score_seq` 의 `LAST_INSERT_ID(score_seq+1)` 로 발급 → 같은 시즌의 모든 점수 기록이 한 행을 잠금. 잠금 시간에 Redis 왕복까지 포함되어 **시즌당 초당 200~300건**이 상한, 서버를 늘려도 개선 안 됨 |

| 항목 | 변경 후 |
|---|---|
| 순서 번호 | 앱에서 시간 기반 발급 `(ms) × 1000 + 서버번호 × 100 + 순번` — 중앙 잠금 없음, 시계 역행에도 단조 증가 |

### 테스트 추가

단위 6건(대량 발급 유일·증가, 시계 역행, 서버 간 순서, 범위). 통합 3건(20명 동시 같은 점수 → 전원 반영·기록 순서 정렬, 같은 회원 15건 동시 → 최고 점수 하나, 재구성 따라잡기).

### 발생 이슈

1. **갭 락 데드락 (통합 테스트에서 발견)** — 처음엔 `SELECT … FOR UPDATE` 로 기존 점수를 조회한 뒤 INSERT/UPDATE 했다. 행이 없으면 InnoDB(REPEATABLE READ)는 그 자리의 **빈 구간(gap)** 을 잠그는데, 갭 락끼리는 서로 호환돼 여러 트랜잭션이 동시에 잡고, 이어지는 INSERT 의 삽입 의도 락이 서로의 갭 락과 충돌해 데드락(`ER_LOCK_DEADLOCK`). 서로 다른 회원이 동시에 **첫 점수**를 낼 때 발생.
   → `INSERT … ON DUPLICATE KEY UPDATE` 한 문장(조건부 SET, `score` 를 마지막에 갱신)으로 변경. 반영 여부는 저장된 `achieved_seq` 가 내 번호인지로 판단. 데드락 자동 재시도(최대 2회)도 적용.
   교훈: "없을 수도 있는 행"을 `FOR UPDATE` 로 미리 잠그지 말 것 (재화 원장은 처음부터 ODKU 로 행을 확보한 뒤 잠가서 이 문제가 없었음).
2. **ODKU SET 순서가 바뀌어 기록 시각이 갱신 안 됨 (통합 테스트에서 발견)** — MySQL 은 `ON DUPLICATE KEY UPDATE` 의 SET 을 왼쪽부터 평가하고 뒤 항목은 앞에서 바뀐 값을 본다. 그래서 `score` 를 마지막에 두었는데, Drizzle 의 `onDuplicateKeyUpdate({ set })` 는 객체에 쓴 순서가 아니라 **테이블 컬럼 정의 순서**(score → achieved_at → achieved_seq)로 SET 을 만든다. score 가 먼저 바뀌어 `IF(VALUES(score) > score, …)` 가 항상 거짓 → 최고 점수를 경신해도 기록 시각·순서 번호가 그대로였고, 반영 여부 판단도 실패해 Redis 동기화가 빠졌다.
   → 이 문장만 `tx.execute(sql\`…\`)` 로 직접 작성해 SET 순서를 고정. 다른 ODKU(시드·KPI·재화·아이템)는 SET 항목끼리 참조하지 않아 영향 없음을 확인.
   교훈: 순서에 의존하는 SQL 은 ORM 빌더에 맡기지 말고 직접 쓴다.

### 피드백 반영

- 원장에서 회원 ID 를 누르면 회원 상세로 이동해 메뉴가 "회원 관리"로 바뀌는 문제 → 재화 관리 화면에 머물도록 변경. 회원 ID 클릭 = 그 회원으로 원장 필터 + **회원 재화 요약 카드**(보유 재화 / 최대 보유, 해당 회원 고정 지급·회수 버튼, 회원 상세 링크, 필터 해제). 회원 상세의 재화 원장 탭은 그대로 링크 없이 표시

### 설계 메모

- 대량 지급은 전부 성공 또는 전부 실패(서버 트랜잭션 하나). 화면에서도 이 점을 경고로 명시
- 권한별 노출: 지급·회수 버튼은 `currency:grant` 또는 `currency:deduct`, 대량 지급 탭은 `currency:grant` 가 있을 때만

### 대량 지급: 회원 ID 직접 입력 → CSV·엑셀 업로드 + 회원별 수량 (피드백)

- **결정**: 파일 형식은 CSV + 엑셀(.xlsx), 수량은 회원별. 사용자 승인 후 진행
- **추가 피드백 → 파일 하나로 완결**: 기본 재화·기본 수량 입력칸과 붙여넣기 입력을 없애고, **사유도 파일 열로** 받음. 파일 열은 회원ID·재화·수량·사유(모두 필수), 사유는 행마다 원장·감사 로그에 기록. 화면의 공통 사유 입력칸 제거
- **추가 피드백 → 행별 재화**: 재화도 행마다 지정(파일 열: 회원ID·재화·수량). 같은 회원에게 여러 재화를 한 번에 지급 가능, 중복 판단은 회원+재화 조합. 한도는 인원 1,000명·행 3,000건, 승인 기준은 서로 다른 회원 100명
- **API** `POST /currencies/bulk-grant`
  - 요청을 `entries: [{ publicId, currencyCode?, amount, reason? }]`(행별, 행에 비운 재화·사유는 요청 값) 또는 `currencyCode + publicIds + amount`(전원 같은 지급) 두 형태로 받고, 공유 스키마에서 모든 행에 재화·사유가 채워진 `entries` 로 정규화(요청 단위 reason 필드는 정규화 결과에서 제거). 두 형태를 섞거나 회원+재화가 중복되면 400
  - 재화 존재(`INVALID_CURRENCY` + `invalidCurrencies`)와 재화별 1인당 상한(`EXCEEDS_GRANT_LIMIT` + `overLimit[{publicId,currencyCode,amount,limit}]`)을 요청 시점·승인 후 실행 시점 모두 검사
  - 잠금 순서를 (회원 id, 재화 id) 로 고정해 데드락 방지, 감사 로그는 행마다
  - 응답 `{ count(건), userCount, totals[{currencyCode, amount}] }`
  - 승인 요약: 재화 1종이면 "GOLD 50개 × 3명 지급" / "GOLD 총 1,230개 · 3명 지급 (1인 30~1,000개)", 여러 재화면 "3명 · 5건 지급 (GOLD 1,200개, GEM 5개, FREE_GEM 10개 외 1종)"
  - 호환: 이미 쌓인 승인 요청의 payload(`publicIds + amount`)도 같은 스키마로 읽어 실행 가능 (worker-jobs 테스트가 이 형태로 검증)
- **웹**
  - 파일은 브라우저에서만 읽고 서버에는 검증된 목록만 전송 (업로드 저장소·파일 검사 서버 불필요)
  - CSV: UTF-8 아니면 EUC-KR 로 다시 읽음(한글 엑셀의 "CSV로 저장" 기본값), 따옴표·쉼표 숫자("1,000")·탭 구분(엑셀 복사 붙여넣기) 지원
  - 엑셀: `read-excel-file` (읽기 전용, 필요할 때만 동적 로딩). SheetJS(`xlsx`)는 npm 배포판(0.18.5)에 알려진 취약점(프로토타입 오염·ReDoS)이 남아 있어 제외
  - 열: 회원ID·재화·수량·사유. 머리글이 있으면 이름으로 열을 찾고(순서 무관), 없으면 이 순서로 읽음. 재화는 코드(대소문자 무시) 또는 이름("골드"), 사유는 5~200자(쉼표가 든 사유는 CSV 따옴표로)
  - 행별 오류(형식·없는 재화·재화별 상한 초과·사유 누락/길이·회원+재화 중복)를 미리보기 표에 행 번호와 함께 표시, 오류가 하나라도 있으면 지급 버튼 비활성. 재화별 합계를 태그로 표시
  - 양식 CSV 다운로드(UTF-8 BOM), 파일 2MB·1,000행 제한

- `FREE_GEM`(무료 젬, id 4, 무료 재화, 최대 9,999,999, 1회 상한 10,000) 추가, 기존 `GEM` 이름을 "유료 젬"으로 변경 (코드는 그대로)

### 발생 이슈

1. **시즌 겹침 잠금을 커밋 전에 해제 (작성 중 발견)** — 처음엔 트랜잭션 안에서 `GET_LOCK` 을 잡고 커밋 전에 `RELEASE_LOCK` → 다음 요청이 아직 커밋 안 된 시즌을 못 보고 통과할 틈. 잠금을 별도 연결에서 잡고 **커밋 후 해제**하는 `createNamedLock` 으로 변경 (동시 생성 테스트 추가)

2. **통합 테스트 6건 실패 — DATETIME 반올림 (첫 실행)** — 시드가 시즌 시작을 `new Date()`(예: 22.700초)로 넣으면 MySQL `DATETIME` 이 **반올림**해 23초로 저장 → 최대 0.5초 미래. 새로 넣은 "진행 중 시즌만 점수 기록" 검사가 직후 기록을 "시작 전"으로 거부, live-ops 도 시즌을 못 찾음. 조기 종료도 같은 이유로 바로 종료 처리가 안 될 수 있었음.
   → DB 에 쓰고 곧바로 비교하는 시각은 `floorToSecond` 로 **초 단위 내림**: 시드 시즌 시작, 일정 시작·종료, 조기 종료 시각 (단위 테스트 추가). refresh 토큰 재사용 판정 때와 같은 함정 — 교훈: DATETIME(0) 컬럼에 "지금"을 넣고 비교할 땐 내림

- **삭제**: approvals 모듈·라우터, `approval_requests` 테이블, `ranking_reward_payouts.approval_request_id`, `approval:review` 권한(시드가 DB 에 남은 권한·역할 연결·개별 부여 정리), Worker `approvals-maintenance`(기동 시 BullMQ 스케줄도 제거), 승인함 메뉴·화면·배지, 대시보드 "대기 중인 승인" → "게임 상태(점검 여부)" 카드로 교체
