# 점검 · 공지 관리 설계

> 상태: **구현 완료** (2026-11-15 승인, 2026-11-16 테스트·화면 확인)

## 1. 결정 사항 (2026-11-15 사용자 선택)

| 항목 | 결정 |
|---|---|
| 점검 차단 대상 | **게임 유저만**. 백오피스 운영자는 점검 중에도 작업 가능 (보상 처리 등) |
| 예외 허용 | 점검마다 접속 허용할 **회원 ID 목록**(테스트·QA 계정) |
| 점검 방식 | **예약**(시작·종료 시각) + **긴급**(지금 바로). 진행 중 점검은 "지금 열기"로 앞당겨 끝낼 수 있음 |
| 공지 형태 | **공지사항 목록 + 로비 한 줄 공지(티커)** 둘 다 |

## 2. "접속 차단 · 세션 종료"를 어떻게 구현하나

이 프로젝트에는 실제 게임 서버가 없고 시뮬레이터가 게임 서버 역할(`/internal/game/*`)을 한다. 그래서 백오피스가 할 수 있는 일과 게임 서버가 할 일을 나눈다.

| 백오피스(이 프로젝트) | 게임 서버(시뮬레이터가 흉내) |
|---|---|
| ① 점검 중이면 게임 API 의 **플레이 요청을 거부** (503 `MAINTENANCE`, 종료 예정 시각·안내 문구 포함). 예외 회원은 통과 | 503 을 받으면 플레이 중단, 안내 표시 |
| ② **세션 세대 번호(sessionEpoch)** 를 점검 시작 때 올리고 live-ops 로 알림 | 접속 중인 유저의 세대 번호가 낮으면 **연결을 끊음** (= 모든 세션 종료) |
| ③ live-ops 에 `maintenance` 정보(진행 중 여부·종료 예정·문구) | 로그인 화면에 점검 안내 |

- 차단 판단은 매 요청마다 하므로 **Redis 에 현재 점검 상태를 캐시**(원본은 DB). 점검 변경 시 즉시 갱신 + 워커 1분마다 재계산. Redis 장애 시 DB 로 판단(느려도 정확)
- 차단 대상 API: 이벤트(로그인·플레이), 점수, 재화, 우편 수령 — 회원 샘플 조회·live-ops·공지 조회는 열어 둠(점검 안내를 받아야 하므로)

## 3. 데이터

```
maintenances
  id, title(≤50), message(≤500, 유저에게 보이는 문구)
  starts_at, ends_at(예정)
  started_at   -- 실제 시작 처리 시각 (세션 세대 번호를 올린 시점)
  ended_at     -- "지금 열기"로 앞당겨 끝낸 시각
  canceled_at  -- 시작 전 취소
  allow_public_ids JSON (≤100명)
  session_epoch -- 시작할 때 부여한 세대 번호
  notice_id     -- 같이 만든 점검 공지
  version, created_by, updated_by, created_at, updated_at

notices
  id, category(NOTICE 안내 | UPDATE 업데이트 | EVENT 이벤트 | MAINTENANCE 점검)
  title(≤60), body(≤5000, 평문 — HTML 불가)
  starts_at, ends_at(NULL=계속)
  pinned        -- 목록 상단 고정
  ticker_enabled, ticker_text(≤80)  -- 로비 한 줄 공지
  hidden_at     -- 내리기
  maintenance_id
  version, created_by, updated_by, created_at, updated_at
```

- 점검 상태(예정·진행·종료·취소)는 시각으로 계산. 점검은 **기간이 겹칠 수 없음** (이름 잠금, 커밋 후 해제)
- 세션 세대 번호는 전역 단조 증가 (`game:session-epoch`, DB 에도 기록)

## 4. 점검 흐름과 위험도

| 작업 | 위험도 | 내용 |
|---|---|---|
| 예약 점검 등록·시작 전 수정·취소 | L1 | 사유 필수. 점검 공지를 함께 만들고(기본 켬) 시간 바뀌면 공지도 갱신, 취소하면 공지도 내림 |
| **긴급 점검 (지금 시작)** | **L2** | 확인 화면에 "최근 30분 접속 회원 약 N명이 끊깁니다" + 종료 예정 시각. 확인 후 즉시 차단·세션 세대 증가 |
| 예약 점검의 실제 시작 | 자동 | 워커(1분)가 시작 시각에 세션 세대 증가 + 시작 기록 (조건부 UPDATE 로 한 번만) |
| **진행 중 점검 연장** | **L2** | 종료 예정 시각만 변경 가능 |
| **진행 중 점검 지금 열기** | **L2** | 즉시 차단 해제 |
| 진행 중 예외 회원 변경 | L1 | QA 계정 추가 등 |

- 백오피스 상단에 **"게임 점검 중 (~06:00)"** 띠를 모든 운영자 화면에 표시 (실수로 점검 중임을 모르고 작업하지 않게)
- 권한 신설: `maintenance:manage`(최고 관리자·운영자), `notice:read`(전 역할), `notice:manage`(최고 관리자·운영자·고객지원)

## 5. 공지

- 게시 기간 동안 게임에 노출, `pinned` 는 목록 맨 위, 나머지는 최신순
- 티커: 게시 기간 중 `ticker_enabled` 인 공지의 `ticker_text` 를 live-ops 로 (최대 5개, 고정 → 최신순)
- 본문은 **평문만** (게임 클라이언트가 HTML 로 그리다 스크립트가 실행되는 일 방지). 줄바꿈만 유지
- 내리기(hidden_at) L1, 수정 L1 — 게임에 바로 반영

## 6. 게임용 API

| Method | Path | 점검 중 |
|---|---|---|
| GET | `/internal/game/live-ops` | 열림 — `maintenance`, `sessionEpoch`, `tickers[]` 추가 |
| GET | `/internal/game/notices` | 열림 — 게시 중 공지 목록 (고정 → 최신) |
| POST | `/internal/game/events`·`scores`·`currencies`, 우편 수령 | **503 MAINTENANCE** (예외 회원 제외) |

시뮬레이터: 503 을 받으면 그 틱의 플레이를 멈추고 "점검 중 (~종료 예정)" 로그, sessionEpoch 가 바뀌면 "세션 종료" 로그

## 7. 화면 `/live-notices` (메뉴: 점검·공지)

- **점검 탭**: 지금 상태 카드(진행 중이면 빨강, 남은 시간·예외 회원), 예정·지난 점검 목록, "점검 예약", **"긴급 점검"**(빨간 버튼) / 진행 중이면 "연장"·"지금 열기"
- **공지 탭**: 목록(분류·기간·고정·티커·상태), 편집 서랍(분류, 제목, 본문, 기간, 고정, 티커 문구), 내리기
- 백오피스 공통 상단 띠: 점검 진행 중 표시

## 8. 범위 밖

- 실제 게임 클라이언트·서버의 연결 끊기 구현 (신호만 제공, 시뮬레이터가 흉내)
- 다국어 공지, 서버(월드)별 점검
- 공지 읽음 집계

## 9. 테스트 계획

예약 점검 자동 시작(동시 워커 한 번)·세션 세대 증가, 긴급 점검 L2, 점검 중 게임 API 503 / 예외 회원 통과 / live-ops·공지는 열림,
지금 열기 L2 후 즉시 해제, 연장 L2, 점검 기간 겹침 409(동시 요청), 점검 공지 자동 생성·시간 동기화·취소 시 내림,
공지 게시 기간·고정 순서·티커, 본문 HTML 그대로 평문 저장, Redis 장애 시 DB 판단
